# 文献工作文件管理与 GitHub 保存方案

状态：待确认草案，尚未作为正式规则生效。

本文用于与后续提供的提示词 Markdown 文件配合使用。尚未收到或核对的提示词不视为已整合；出现冲突时，列出冲突并向用户提问，不自行覆盖已确认规则。

## 1. 文件保存原则

- 使用 Markdown 保存阅读笔记、分析、决策、索引和交接记录。
- 代码、图片、表格和文献原文件保留适合其用途的格式，不强行转换为 Markdown。
- GitHub 保存已提交并成功推送的成果；云环境用于处理文件和执行任务。聊天记录、未提交文件和未推送提交不会自动保存在 GitHub。
- 文献原文件的上传需考虑版权、隐私及仓库容量。无法上传时，在笔记中保存准确的题录、DOI、来源链接和原文件位置。链接不保证永久可访问，不能替代原文件备份。
- 密钥、密码和访问凭据不得写入文档或提交到仓库。使用 GitHub 前确认仓库可见性适合文件内容。

## 2. 推荐目录

以下为建议结构，按实际需要创建目录；尚无内容的目录不必建立。Git 不保存空目录。

```text
README.md                         # 总入口：说明目录、阅读入口与保存方式
rules/
  README.md                       # 列出已确认规则及其适用范围
  confirmed/                      # 经用户确认的规则
  proposals/                      # 尚未确认的新增要求和修改建议
prompts/
  README.md                       # 提示词用途、状态和关联规则
  originals/                      # 用户提供的提示词原文
  proposals/                      # 提示词修改建议，保留与原文的对应关系
literature/
  index.md                        # 文献编号、题目、主题、阅读状态及笔记链接
  notes/                          # 每篇文献的阅读笔记
  syntheses/                      # 跨文献比较、综合分析与阶段性结论
  sources/                        # 允许保存且适合入库的文献原文件
assets/                           # 笔记引用的图片、图表等附件
work/
  current.md                      # 当前任务、关键结论、阻塞与下一步
  handoffs/                       # 阶段性交接记录
```

文件使用相对链接互相引用。README、文献索引和当前任务文件是三个主要入口，不把所有正文集中到一个大文件里。

## 3. 文件命名

文件名默认采用小写英文、数字和短横线；标题与正文可使用中文。避免空格、含义不明的缩写和“最终版2”等名称。

| 类型 | 格式 | 示例 |
| --- | --- | --- |
| 长期维护说明 | `主题.md` | `github-backup.md` |
| 单篇文献笔记 | `编号-简短主题.md` | `lit-0001-memory-retrieval.md` |
| 跨文献分析 | `主题.md` | `retrieval-method-comparison.md` |
| 阶段性交接 | `YYYY-MM-DD-主题.md` | `2026-10-15-reading-handoff.md` |
| 规则提案 | `编号-主题.md` | `proposal-0001-note-template.md` |
| 附件 | `文献编号-用途.扩展名` | `lit-0001-method-diagram.png` |

文献编号分配后保持不变；新增编号前检查索引，避免重复。日期仅用于有时间属性的记录。同一天需要多份同主题记录时追加序号。文件历史交给 Git 管理，不通过反复复制文件保留版本。

## 4. 阅读笔记的建议内容

每篇笔记应能在脱离原对话后独立理解，建议包括：

1. 文献编号、完整题录、DOI 或来源链接、原文件位置。
2. 阅读状态及实际阅读范围，例如全文、指定章节或仅摘要。
3. 研究问题、方法、主要发现及适用条件。
4. 支撑结论的页码、章节、表格或图编号；无法定位时明确标记待核实。
5. 本次形成的分析、与其他文献的联系、分歧和局限。
6. 尚未解决的问题、需要用户判断的事项及下一步。

区分作者结论、文献中的直接证据、助手推断和待验证假设。未读内容不得写成已经验证的结论。跨文献分析引用对应笔记和证据位置，减少重复抄写。

## 5. 保存与推送流程

每完成一个可独立理解的阅读或分析单元，或准备结束当前工作时：

1. 保存笔记或分析，并更新文献索引。
2. 更新 `work/current.md`，记录当前进度、关键文件、阻塞和下一步。
3. 检查差异及待提交文件，排除凭据、缓存、临时输出和不应上传的文件。
4. 将本次相关文件提交，使用明确的提交说明，例如 `docs: add notes for lit-0001`。
5. 在已获用户授权且具备访问权限时推送到 GitHub，并核实目标分支的远程提交与本地提交一致。

提交与推送是不同步骤。推送失败时保留本地成果，明确报告哪些内容仍未保存到远程，不将其描述为已备份。不要强制推送或覆盖远程历史；发生冲突时先保留双方内容并向用户说明。

起步阶段可使用单一主分支；是否直接推送主分支应遵循用户授权和仓库保护设置。较大修改可使用分支及 Pull Request。GitHub 上的删除和修改也会同步影响后续检出；重要阶段可另设标签，并按需要保留独立备份。

## 6. 新对话或新云环境中的恢复顺序

1. 打开或检出仓库，确认分支和提交；已有本地修改时先检查，避免覆盖。
2. 阅读 `README.md`、`rules/README.md` 及适用的已确认规则。
3. 阅读 `prompts/README.md` 和本次需要使用的提示词。
4. 阅读 `work/current.md`，再按需查阅最近的交接记录。
5. 通过 `literature/index.md` 找到相关笔记和综合分析，核对依据后继续。

恢复应依赖仓库中的明确记录，不声称已经记得未读取的旧对话。已丢失且从未推送的文件无法通过 GitHub 补回；可以从仍可访问的聊天或其他备份中整理恢复，并注明来源和缺失部分。

## 7. 困难、冲突与规则变更

- 遇到阻碍正确性或后续工作的难题，及时向用户提问，说明问题、已尝试的方法、影响及建议选项；不忽略问题，也不无期限独自排查。
- 等待答复时，可继续不依赖该答案的工作。未决事项记录在 `work/current.md`。
- 用户新提出的要求和助手建议的优化先进入 `rules/proposals/`，注明来源、理由、影响文件和待确认问题，不直接写入已确认规则。
- 助手提出优化时，必须明确说明改动内容并提问；未经确认，不将建议标记为正式规则。
- 经用户确认后，再更新相关规则及索引，并通过 Git 提交保留变更记录。规则与提示词存在冲突时先提问，不自行选择覆盖。
